# 六类报告骨架

每类都按「**读者的问题顺序**」排，不按「你的工作顺序」排。
读者第一眼问的永远是「所以呢」，不是「你怎么做的」。

通用规矩：

- **每份报告顶部都有一个页眉带**：标题 / 一句话结论 / 生成时间 / 数据截止时间。四项缺一不可，**生成时间和数据截止时间不是一回事**，分开写。
- **结论写在最上面**，展开写在下面。不要"最后得出结论"。
- **过程只写影响结论的那部分**。你试错了三次但不改变结论，就不要写。
- **不确定的地方要标出来**，用一句话说明不确定在哪、要什么才能确定。宁可写"这条没查到"，也不要含糊带过。

---

## ① 完工报告 task-completion

**回答的是**："我让你做的事做完了吗，我要不要复查？"

| 块 | 放什么 | 不能省 |
|---|---|---|
| 结论带 | 做完了 / 部分做完 / 没做完 + 一句话 | ✅ |
| 做了什么 | 按交付物列，不按步骤列 | ✅ |
| 改动清单 | 动了哪些东西，每条一行，带位置 | ✅ |
| 怎么验证的 | 跑了什么、结果是什么；**没验证就写"未验证"** | ✅ |
| 遗留与下一步 | 没做的、需要人接手的 | ✅ |

⚠️ "怎么验证的"这一块是这类报告的价值所在。写不出具体验证动作，说明这份报告不该叫完工报告。

## ② 调研报告 research

**回答的是**："结论是什么，我能信吗？"

结论 → 依据（每条结论下挂支撑它的事实）→ 分歧与不确定 → 出处清单。

- **每一条结论都要能追到出处**。追不到的单独放进「未证实」块，不要混在结论里。
- 出处写清楚是哪份文件/哪个系统/哪一页，不要只写"根据资料"。
- 有互相矛盾的资料，把矛盾**摆出来**并说明你采信哪一边、为什么。

## ③ 审查报告 audit

**回答的是**："哪里不合格，严重吗，先修哪个？"

总评 → 逐条通过与否 → 发现（按严重度排）→ 建议动作。

- 逐条表是这类报告的主体：**条目 / 结论(通过·不通过·不适用) / 实际值 / 要求值 / 证据**。
- 发现按严重度排序，**严重度是给读者排优先级用的，不是形容词**：定义清楚每一级是什么意思。
- 每条发现配一条可执行的建议动作，写"改成什么"而不是"应加强"。

## ④ 受阻报告 blocker

**回答的是**："卡在哪，谁来解，我现在能干什么？"

卡点 → 根因 → **需要谁做什么**（带姓名/角色和期限）→ 临时绕法 → 影响面。

- 这类报告的主角是「**需要谁做什么**」，放在最显眼处，不要埋在下面。
- 根因和现象要分开写。"接口报错"是现象，"对方系统换了证书"才是根因；查不到根因就明说"根因未定位"。
- 临时绕法要写清代价（慢多少、漏什么、要人工做什么）。

## ⑤ 对比报告 comparison

**回答的是**："选哪个？"

推荐与理由 → 对比表 → 逐维展开 → 什么情况下换选择。

- **先给推荐**。列完三个选项让读者自己选，等于没做这份报告。
- 对比表每一维都要能分出高下；"都还行"的维度删掉。
- 最后一块「什么情况下换选择」是专业度的体现：说明推荐成立的前提，前提变了该换哪个。

## ⑥ 进度报告 status

**回答的是**："整体到哪了，哪里要我管？"

| 块 | 放什么 |
|---|---|
| 结论带 | 整体是否在计划内 + 最需要关注的那一个对象 |
| 对象看板 | 每个对象一格：名称 / 当前阶段 / 是否延期 / 下一节点日期。**横排成一行便于横向比较**，不要纵向堆成长列表 |
| 时间线 | 关键节点与今天的位置 |
| 异常明细 | 只列延期或有风险的，正常的不占版面 |
| 本期变化 | 与上期相比，哪些动了 |

- 正常项不铺开，**版面留给异常项**。全绿的周报应该很短。
- 每个延期项都要有原因和新日期；原因长就折叠起来（`<details>`），默认收起。
